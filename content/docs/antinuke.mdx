## Why use an antinuke system?

AntiNuke helps you keep moderators and other trusted members within the limits you set for your server. If someone starts abusing destructive actions and goes over the threshold you configured, bored applies the punishment you chose before the damage can continue.

## How does the antinuke work?

Each AntiNuke module watches a specific action type and counts how often one person does it within a short window. Once that count passes the threshold you set, bored applies the configured punishment and logs what happened for the server owner to review.

## Start here

<Steps>
  <Step title="Run `antinuke setup`">
    This applies bored's recommended configuration.

```text
antinuke setup
```

    It enables protection for dangerous permission grants, channel creation and deletion, role deletion, emoji deletion, mass bans, mass kicks, webhook creation, and bot joins. Vanity protection is left for you to enable separately if you want it.
  </Step>
  <Step title="Review the current state">
    Use `antinuke config` to see the status of each module, or `antinuke list` to view enabled modules together with whitelist and protected-target entries.
  </Step>
</Steps>

<Callout type="info" title="Bulk toggle">
Use `antinuke toggle on` or `antinuke toggle off` to enable or disable the normal AntiNuke modules without resetting their saved thresholds, punishments, or command-detection settings.
</Callout>

## Who can manage it

The **server owner** is an antinuke admin by default. If you want someone else to manage it too, add them as an antinuke admin.

AntiNuke does not punish the server owner, antinuke admins, or whitelisted users.

<Callout type="info" title="bored vanity">
The companion [**bored vanity**](https://discord.com/oauth2/authorize?client_id=1459869503289561293) bot is always whitelisted from antinuke by default, so role awards and its join do not trigger modules like `botadd` or `role`. That whitelist entry cannot be removed.
</Callout>

## Whitelist

Whitelisted members and bots bypass AntiNuke completely, so only use this for targets you 100% trust.

### Whitelist a member or bot

<Tabs items={["Syntax", "Example"]}>
  <Tab>

```text
antinuke whitelist (member)
```

  </Tab>
  <Tab>

```text
antinuke whitelist @trusted-mod
```

  </Tab>
</Tabs>

You can use a mention, username, or raw ID here. `antinuke wl` works as a shorter alias.

### Whitelist every current bot

```text
antinuke whitelist bots
```

This bulk-whitelists the bots that are already in the server so you do not have to whitelist each one by hand.


  </Tab>

    Decides whether bored's own commands count toward the threshold. Use it on `ban`, `kick`, `role`, `webhook`, and `permissions`.

#### More on the command flag

For instance, a moderator could try to abuse their permissions through bored itself by using the `ban` command on each member one by one. When `--command` is set to `on`, those command-based actions count toward the threshold and can trigger AntiNuke.

## AntiNuke Protect

`antinuke protect` lets you mark one specific user or one specific role as protected from kicks and bans.

If somebody who is **not** the server owner or an antinuke admin tries to kick or ban that protected target, bored treats it as a serious antinuke event. bored can punish the actor, log it as an automatic case, and DM the server owner.

This is especially useful for your **Server Booster** role. That role cannot be deleted or manually removed from active boosters unless the member stops boosting, so protecting it gives you a clean way to punish anyone who tries to kick or ban boosters through bored or through Discord's native moderation.

### Protect a user or role

<Tabs items={["Syntax", "Example"]}>
  <Tab>

```text
antinuke protect (role/user) (punishment)
```

  </Tab>
  <Tab>

```text
antinuke protect @Server Booster stripstaff
```

  </Tab>
</Tabs>

In this example, anyone who is not an antinuke admin and tries to kick or ban a member with the `@Server Booster` role will be punished with `stripstaff`.

If you run the same command again with the same target and punishment, bored removes that protection. If you run it again with a different punishment, bored updates the punishment instead.

### What happens when protection is triggered

- If the protected target is acted on through bored's own `ban`, `softban`, `tempban`, or `kick` commands, bored blocks the action first unless the moderator is the server owner or an antinuke admin.
- If the protected target is acted on natively through Discord, bored allows the native action to happen and then punishes the responsible moderator through AntiNuke.
- Protected users and protected roles also appear in `antinuke list`. Use `antinuke protected` or `antinuke protect list` to view only protected targets.

## Modules

### Ban protection

<Tabs items={["Syntax", "Example"]}>
  <Tab>

```text
antinuke ban (on or off) [--threshold (number)] [--do (punishment)] [--command (on or off)]
```

  </Tab>
  <Tab>

```text
antinuke ban on --threshold 3 --do stripstaff --command on
```

  </Tab>
</Tabs>

In this example, `threshold` being set to `3` means AntiNuke triggers after `3` bans. `do` being set to `stripstaff` means the person responsible has their staff roles removed, and `command` being on means bans done through bored's `ban` command still count.

### Dangerous permission grants

<Tabs items={["Syntax", "Example"]}>
  <Tab>

```text
antinuke permissions (on or off) [--threshold (number)] [--do (punishment)] [--command (on or off)]
```

  </Tab>
  <Tab>

```text
antinuke permissions on --threshold 1 --do ban --command on
```

  </Tab>
</Tabs>

Enabling this means bored will monitor dangerous permission grants by default. The bulk watcher defaults to threshold `1`, so a single dangerous grant can trigger immediately. In the example above, `do` being set to `ban` bans the responsible member, and `command` being on means bored's own role commands can be blocked from granting dangerous permissions when command detection applies.
